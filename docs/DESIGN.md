# 设计文档

## 1. 要解决的问题

链上机会的生命周期大致是：

```
资金悄悄进场 → 价格开始动 → 小圈子讨论 → KOL 转发 → 热搜 → 散户接盘
     ↑              ↑            ↑
   最难发现      本工具目标区间   已经晚了
```

绝大多数工具盯的是最后两段（热搜榜、涨幅榜），那时候已经没有超额收益了。这个工具盯中间那段：**资金已经动了，注意力刚开始扩散**。

单维度都不够用：

- **只看资金面**：链上每天几万个新池，放量的一大半是机器人对敲或者拉盘出货，噪音比信号多两个数量级。
- **只看注意力面**：X 上的加密话题里营销号占绝大多数，单人刷屏和真实扩散在提及量上看起来一模一样。

所以核心设计是**共振**：两个噪音结构完全不同的维度在同一时间窗内同时异常，才是真信号。营销号刷屏不会带来真实资金流入，机器人对敲也不会引发真人讨论。

## 2. 架构

```
collectors/          detect/              alerts/
  dexscreener  ──┐     baseline.py  统计量   telegram
  geckoterminal  │     anomaly.py   规则判定  discord
  defillama      ├──▶  fusion.py    融合打分  console
  evm_wallets    │                          web/ 看板
  solana_wallets │        ▲
  x_attention    │        │
  free_attention ┘   storage/db.py (SQLite 时间序列)
```

每个采集器只做一件事：把外部数据变成 `(实体, 指标, 时间戳, 值)` 四元组。之后的检测、打分、告警完全不关心数据从哪来——所以换 X 供应商、加一条新链、接一个新数据源，都只是加一个采集器，下游一行不用改。

**实体**有四类：`token`（代币）、`chain`（链）、`narrative`（叙事/赛道/关键词）、`wallet`。所有指标都挂在实体上，同一套检测逻辑对四类实体通用——「Solana 链上稳定币异常流入」和「某个 meme 币成交量异常放大」走的是同一条代码路径。

**存储**用 SQLite 单文件。指标表是 `(entity_id, metric, ts)` 复合主键的 `WITHOUT ROWID` 表，读写都是主键顺序扫描，几百万点也不慢，而且零运维、可以直接拷走、GitHub Actions 用 cache 就能带走状态。

## 3. 异常检测

### 3.1 为什么用中位数 / MAD 而不是均值 / 标准差

加密市场的指标序列本身就充满尖峰。用均值和标准差会出现**掩蔽效应**：

```
历史: [100, 101, 99, 100, 5000, 100, 98, 102]   # 5000 是几小时前的一次异动
当前值: 400

均值+标准差:  均值 712.5，标准差 1732 → z = -0.18，判定「正常」  ← 漏报
中位数+MAD:   中位数 100，MAD 1     → z = 202，判定「异常」    ← 正确
```

一次历史异动就把后续所有异动的检测能力毁掉了，这在实践中非常致命。中位数和 MAD 有 50% 的崩溃点，一半数据是异常值都不影响估计。

MAD 为 0（序列长期恒定）时退化到平均绝对偏差；两者都为 0 时给一个固定分数——这在 `x_kol_mentions` 这种长期为 0 的指标上很常见。

### 3.2 检测方法

| 方法 | 判定 | 适合的形态 |
|------|------|-----------|
| `robust_z` | 稳健 z 分数超阈值 | 成交量、提及量这类有稳定基线的指标 |
| `ratio` | 当前值 / 基线中位数超倍数 | 5m 成交量这类波动大、基线可能接近 0 的 |
| `delta_pct` | 相对 N 个点前的百分比变化 | 流动性注入 / 撤出 |
| `acceleration` | 近段变化幅度 / 上段变化幅度 | 区分「刚起步」和「已经走完」 |
| `level` / `level_below` | 绝对阈值 | 聪明钱地址数、买卖比这类有天然含义的 |

`level` 类规则不需要历史，冷启动第一轮就能生效；其它方法需要至少 `min_samples`（默认 8）个历史点，否则不判——宁可漏也不要在数据不足时瞎报。

每条规则还有 `min_value` 绝对值闸门。这个很重要：成交量从 2 美元涨到 20 美元在比例上是 10 倍，但毫无意义，必须挡掉。

### 3.3 打分曲线

单条规则的得分是 `100 * r / (1 + r)`，其中 `r = 观测值 / 阈值`：

| r | 1 | 2 | 4 | 9 | 20 | 100 |
|---|---|---|---|---|----|-----|
| 分数 | 50 | 67 | 80 | 90 | 95 | 99 |

刻意不用线性映射。真实异动的 z 分数动辄几十上百，线性映射会让绝大多数信号都顶到 100 分，「放量 5 倍」和「放量 50 倍」变成同一个分数，排序就失去意义了。这条饱和曲线在任何量级上都还留着区分度，同时永远不会超过 100。

## 4. 融合打分

```
资金分   = noisy_or(所有资金面信号得分)
注意力分 = noisy_or(所有注意力面信号得分)
风险扣分 = noisy_or(所有风险信号得分) / 100 * 扣分上限

总分 = 0.55 × 资金分 + 0.45 × 注意力分
      + 共振加成（两面都触发时 +15）
      + 早期加成（市值越小越高，最多 +12）
      - 风险扣分（最多 -45）
```

**noisy-OR** = `100 × (1 - Π(1 - sᵢ/100))`。比「取最大值」更能体现证据叠加（三个 60 分的独立信号确实比一个 60 分强），又比「求和」合理（不会因为规则写得多就轻易爆表），而且天然有界。

**共振判定**跨时间窗，不是只看单轮。资金和注意力很少精确同时到达，通常差几十分钟——只比较当前这一轮会漏掉绝大部分真实共振。所以本轮命中一边、另一边在过去 90 分钟内命中过，同样算共振。

**早期加成**按市值对数刻度给，因为这个工具的目的是「早」。同样的异动形态，400 万市值和 4 亿市值的意义完全不同。

**风险一票否决**：光扣分挡不住。资金和注意力都拉满时，减 45 分仍然能过阈值——但「流动性刚被抽走 80%」这种情况无论多热闹都不该推给你。所以风险扣分达到 `risk_veto`（默认 30）直接不告警。它仍然会入库、在看板上可见，只是不打扰你。`demo` 里的 DEMOC 就是这个形态。

## 5. 信号体系

### 资金面

| 规则 | 想抓什么 |
|------|---------|
| `vol_1h_spike` | 有真金白银进来了 |
| `vol_5m_burst` | 刚刚发生的脉冲，时效性最强 |
| `liq_inflow` | 有人在加池子，通常是庄在建仓 |
| `buy_pressure` | 买单笔数显著压过卖单 |
| `smart_money_cluster` | **多个**独立聪明钱同期建仓——单个地址买入意义有限，聚集才值钱 |
| `mcap_accel` | 市值上涨在加速，说明还在早期而不是尾声 |

### 注意力面

| 规则 | 想抓什么 |
|------|---------|
| `x_mention_spike` | 提及量异常 |
| `x_author_spread` | **独立作者数**扩散——这条比提及量重要得多：单人刷 100 条和 50 人各发 1 条，前者是噪音，后者才是扩散 |
| `x_kol_pickup` | 多个 KOL 同期提及，通常领先散户几小时 |
| `x_engagement` | 互动量异常，过滤掉没人理的自嗨 |
| `boost_burst` | DexScreener 付费推广激增——项目方在花钱买注意力，是意图的直接证据 |
| `cg_trending` / `reddit_spike` | 免费代理信号，X 预算用尽时仍有输出 |

### 风险面

| 规则 | 想抓什么 |
|------|---------|
| `liq_drain` | 流动性断崖式撤出，最典型的 rug |
| `wash_trading` | 成交量/流动性比异常高，疑似对敲刷量 |
| `sell_pressure` | 卖压主导，通常是出货阶段 |

## 6. 成本控制

X 是唯一按量计费的数据源，所以有专门的预算机制：

1. **三层上限**：单轮 / 每小时 / 每天，存在 SQLite 里，重启和 Actions 冷启动之间正确累计。
2. **优先级分配**：预算只花在**资金面已经有异动**的标的上。没有资金信号的代币不烧 X 预算——因为单独的注意力异常本来就不可信。
3. **精确查询**：默认用**合约地址**而不是 `$SYMBOL` 检索。地址几乎没有同名噪音，而且「有人在推 CA」本身就是极早期信号。

Solana 聪明钱监控也做了成本优化：不解析交易（每个地址要几十次 RPC 调用），而是用 `getTokenAccountsByOwner` 快照全部代币余额，两次快照做差就知道它在买什么卖什么。精度略低，成本低一个数量级。

## 6.5 榜单类信号必须补零

这是实测数据打脸之后才修对的一个建模问题，值得单独写。

CoinGecko 热搜最初用的是「在榜就触发」的绝对值规则。结果在真实数据上，
BTC、ETH、SOL 每一轮都被判为注意力异常——因为它们常年在榜。

问题的本质是**只记录了「在榜」，没有记录「不在榜」**：榜上的币每轮都是同一个值，
序列是一条平线，任何基于变化的规则都失效，而基于绝对值的规则则每轮都触发。

修法是给掉出榜单的实体补一个 0：

```
不补零：  16, 16, 16, 16, 16   ← 平线，看不出任何事件
补零后：   0,  0,  0, 16, 16   ← 进榜是一次 0 → 16 的跃升，一眼可见
```

规则随之从 `level` 改成 `delta_pct`。常驻榜单的币不再触发，新进榜的会。
所有「榜单 / 排行 / 名单」类的信号都适用这个原则——记录缺席和记录在场同样重要。

## 6.6 探针要区分「必需」和「有回退」

`probe --schema` 一开始把所有依赖字段都当必需，结果持续报红两条：

- `marketCap` 在包装原生代币上本来就没有，而代码有 `marketCap → fdv → gt_fdv_usd` 三级回退
- Reddit 已经默认关闭，探针却还在无条件探它，每次都 403

这两条都不是 bug，但报红一旦变成常态，**真正的字段变更就会被淹没**。
所以探针分成两类期望：`expected` 缺了算失败，`optional` 缺了只提示。
同理，探针只探真正启用的数据源。

顺带一提，这套探针第一版还犯过一个更基础的错误：打的是 `/latest/dex/search`，
而采集器实际用的是 `/tokens/v1`——两个端点字段集不同，等于验错了对象，
还报出了一个根本不存在的 `pairCreatedAt` 缺失。**探针必须打代码真正调用的端点。**

## 6.7 阈值必须按链分档

接入 BSC 和 Robinhood Chain 时踩到的：全局一套阈值在多链场景下必然出错。

Robinhood Chain 是全新链，全网池子数量还是两位数。套用 Solana 的 2 万美元
流动性门槛，等于把整条链直接关掉；反过来为了迁就它把全局门槛降到 3000，
成熟链的噪音就全进来了。

更隐蔽的是**入库前**的灰尘池门槛。第一次接入后实测两轮，BSC 和 Robinhood
一条候选都没有，而 Solana 抓到十几个。排查下来是 `min_reserve_usd: 1000`
这个全局值把新链筛空了——**筛空之后毫无迹象**，日志一切正常，
看起来就像「这条链没有新币」。加了 `per_chain` 覆盖之后：

```
按链拆分（代币 / 信号 / 机会 / 最高分）：
  bsc             43 /  66 /  57 / 63
  solana         114 /  56 /  44 / 65
  robinhood       36 /  26 /  20 / 57
```

所以两件事是配套的：阈值要能按链覆盖，**统计也要能按链拆开看**。
只看总数的话，某条链被静默筛空是发现不了的——总数看起来一直很健康。

## 7. 已知局限

- **X 覆盖不完整**：第三方 API 的检索结果不保证完整，小账号和低互动推文可能漏掉。
- **每条新链的阈值都要重新估**：`filters.per_chain` 和 `geckoterminal.per_chain` 的默认值是按当前池子规模量级估的，不是算出来的。接入新链后先看 `stats` 的按链拆分，某条链长期 0 机会就是阈值卡太死。
- **聪明钱名单要自己维护**：工具不会自动发现聪明钱地址，名单质量直接决定这条信号的价值。
- **风险规则只能挡明显形态**：抽流动性、对敲、卖压主导能挡，蜜罐合约、隐藏 mint 权限、老鼠仓这些挡不住——需要合约层面的静态分析，不在当前范围内。
- **GitHub Actions 实时性和额度都有限**：私有仓库 2000 分钟/月的免费额度下，每次运行按 1 分钟计费（实测 job 只跑 12 秒但按 job 向上取整），30 分钟一跑就占掉 73%。这个频率对 meme 币太慢，只能算兜底；实时监控还是本地 / VPS 常驻。公开仓库无此限制。
- **Reddit 拦数据中心 IP**：在 Actions 和多数 VPS 上稳定返回 403，已默认关闭。本地家宽通常可用。
- **冷启动需要时间**：`min_samples` 默认 8，也就是至少要采集 8 轮（默认 5 分钟一轮 ≈ 40 分钟）之后统计类规则才开始生效。

## 8. 调参建议

先跑一两天积累数据，然后用 `detect` 命令在**已入库的历史数据**上反复试参数——这个命令不发任何网络请求，改完 `config.yaml` 立刻能看到结果差异，不用重新采集。

嫌吵就调高 `score.alert_threshold`，或者提高单条规则的 `threshold` / `min_value`；嫌漏就反过来。`filters` 里的流动性和成交量下限是最有效的降噪手段，比调规则阈值直接。
